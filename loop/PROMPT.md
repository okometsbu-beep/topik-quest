# MALBIT autonomous development prompt

## 1. 합격 기준

이 변경은 일본어를 설명 언어로 쓰는 한국어 완전 초보자가 실제 모바일에서 막힘 없이
사용할 수 있고, 첫 10분 안에 게임·스토리 첫 단계를 완료하게 하며, 재미·재방문성·시장
경쟁력과 정답·해설·번역의 정확성을 동시에 높이는가? 하나라도 아니면 병합하거나
배포하지 않는다.

## 2. 먼저 읽을 문서

매 실행은 이전 대화를 물려받지 않는 새 세션이다. 아래 순서와 범위만 먼저 읽는다.

1. `AGENTS.md` 전체
2. `loop/PROMPT.md` 전체
3. `docs/STATUS.md` 처음 180줄
4. `docs/feedback/INBOX.md` 처음 120줄
5. `docs/DESIGN.md` 처음 220줄
6. 열린 GitHub Issue 중 `[AI 제어]`와 `[AI 지시]` 제목의 본문·최근 댓글만

대형 문제은행 파일과 첨부 ZIP은 콘텐츠 작업이 아닌 한 열지 않는다. 필요한 owning file,
그 심볼의 후속 override, 관련 테스트만 추가로 읽는다.

## 3. 규칙과 근거

1. 한 바퀴에는 정확히 하나의 작은 작업만 완료한다.
   - 왜: 여러 기능을 동시에 건드리면 실패 원인, 되돌릴 단위, 실제 개선 효과가 흐려진다.
2. 열린 `[AI 제어] PAUSE`가 있으면 코드와 문서를 변경하지 말고 이번 바퀴를 종료한다.
   - 왜: 휴대폰에서 즉시 제동할 수 있어야 무인 자동화가 통제 가능한 시스템이 된다.
3. `[AI 지시][긴급]`, 일반 `[AI 지시]`, `docs/STATUS.md`의 다음 작업 순으로 하나를 고른다.
   - 왜: 사용자의 직접 지시를 AI의 추측보다 항상 우선하기 위해서다.
4. 지시가 없으면 `docs/DESIGN.md`의 목표에 가장 크게 기여하는 작은 작업을 스스로 고른다.
   - 왜: 지시가 없는 날에도 제품이 핵심 지표를 향해 전진해야 하기 때문이다.
5. 일본어 설명을 사용하는 한국어 완전 초보자와 첫 10분의 성취를 최우선으로 한다.
   - 왜: 모든 사용자를 동시에 만족시키려 하면 첫 핵심 사용자의 경험도 평범해진다.
6. 정답·해설·번역은 문맥과 근거를 확인하고, 확신할 수 없으면 콘텐츠를 바꾸지 않는다.
   - 왜: 학습 앱에서 그럴듯한 오답은 사소한 UI 결함보다 더 치명적이다.
7. 사용자 저장 키와 기존 진도는 유지하고, 변경이 필요하면 이관 테스트를 먼저 만든다.
   - 왜: 자동 개선이 학습 기록을 지우면 개선이 아니라 사고다.
8. UI 작업은 좁은 모바일 화면, 터치 조작, 뒤로가기, 재진입, 콘솔 오류를 확인한다.
   - 왜: 데스크톱 코드가 정상이어도 실제 휴대폰 경험은 망가질 수 있다.
9. 공개 저장소·정적 GitHub Pages에 비밀키, 개인정보, 유료 서비스 키를 넣지 않는다.
   - 왜: 클라이언트와 공개 Git 기록의 비밀은 이미 유출된 비밀이다.
10. 원문 시험 문제를 복제하지 않고 기존 2,088개 오리지널 문제은행 경계를 지킨다.
    - 왜: 저작권 위험과 제품 신뢰 훼손을 동시에 막아야 한다.
11. 토큰을 아끼기 위해 `AGENTS.md`의 owning-file 경로와 검증 lane을 따른다.
    - 왜: 저장소 전체를 매번 다시 읽는 것은 품질이 아니라 계산비 낭비다.
12. GitHub Pages만 자동 배포하고 양대 스토어 실배포는 별도 release lane 전까지 금지한다.
    - 왜: 서명키, 심사, 단계 배포, 되돌리기 없이 스토어 자동 배포를 켜면 복구가 어렵다.

## 4. 한 바퀴 도는 순서

1. `[AI 제어] PAUSE`를 확인한다. 열려 있으면 변경 없이 결과만 기록하고 끝낸다.
2. 위 문서를 지정된 순서와 범위로 읽는다.
3. `[AI 지시][긴급]` 또는 `[AI 지시]` 하나를 고른다. 없으면 STATUS의 다음 작업 하나를 고른다.
4. 완료 조건과 owning file, 집중 검사를 네 줄 이내로 정리한다.
5. 최신 `main`에서 `agent/loop-<날짜>-<짧은이름>` 브랜치를 만든다.
6. 하나만 구현하고 해당 lane의 자동검사를 실행한다.
7. 검사를 통과하면 화면을 보기 전에 체크포인트 커밋을 남긴다.
8. 화면 변경이면 실제 모바일 크기로 실행해 눈으로 확인하고 콘솔·터치·재진입을 검사한다.
9. 문제가 있으면 같은 브랜치에서 고치고 다시 검사한다. 합격 기준 미달이면 병합하지 않는다.
10. `docs/STATUS.md`에 완료한 일, 검사 결과, 다음 한 작업, 위험을 짧게 갱신한다.
11. PR을 열고 CI가 통과하면 `main`에 squash merge하여 GitHub Pages에 자동 배포한다.
12. 배포 후 라이브 URL을 smoke 확인한다. 실패하면 즉시 revert PR을 만들고 병합한다.
13. 처리한 Issue에 결과·검사·배포 주소·되돌리기 지점을 댓글로 남기고 완료 처리한다.

## 5. 커밋 순서 규칙

검사를 통과하면 화면을 보기 **전에** 일단 커밋한다. 한 바퀴는 도중에 멈출 수 있고,
멈춘 자리에 커밋이 없으면 그 작업은 사라진다. 화면 확인에서 결함을 찾으면 같은 브랜치에
수정 커밋을 추가한다. 체크포인트 커밋은 보존 수단일 뿐이며, 합격 기준을 통과하지 못한
변경은 병합하거나 배포하지 않는다.
